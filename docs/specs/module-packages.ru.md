# Модули-пакеты: установка из zip

Статус: план, согласован 17.10.2026. Реализация начинается после работ по языкам и ускорению портала.

## 1. Цель

Портал состоит из **ядра** и **модулей**. Каждый модуль — отдельный пакет (zip), который суперадминистратор устанавливает, обновляет или удаляет без пересборки портала. При несовместимости портал не ставит модуль и называет, чего не хватает. Позже zip будет приходить из магазина приложений. Механизм тот же, меняется только источник файла.

## 2. Уровни

| Уровень | Состав | Как попадает к клиенту |
|---|---|---|
| Ядро | пользователи, роли, вход, настройки, оформление, уведомления, оргструктура, юрлица, согласования «Ждёт меня», контрагенты, дашборд-оболочка, поиск, помощник, туры, справка, журнал, API, отчёт «Система», языки | в образе портала |
| Базовые модули | задачи, чаты, календарь, файлы, база знаний, онлайн-ресурсы | отдельные пакеты, предустановлены вместе с ядром |
| Устанавливаемые модули | CRM, договоры, закупки, склад, сотрудники, файловый сервер, каталог AD, мастерплан | zip по типу бизнеса |
| Заказные модули | модули под конкретного клиента | zip только этому клиенту; имени клиента нет в коде продукта |

## 3. Принятые решения

1. Базовые модули — отдельные пакеты со своими версиями. Они приходят предустановленными и обновляются zip-файлом.
2. Принимаются только zip с нашей подписью (Ed25519). Без подписи — только в режиме разработки (`MODULES_DEV=1`).
3. Устанавливает, обновляет и удаляет модули только суперадминистратор.
4. При установке и обновлении приложение перезапускается на 5–10 секунд.
5. При удалении модуля данные сохраняются. Полное удаление данных — отдельная кнопка, доступна только после резервной копии.
6. Совместимость задаётся как «версия X или новее». Смена первой цифры версии (1.x → 2.x) считается несовместимой.

## 4. Пакет

```
masterplan-1.2.0.zip
  manifest.json
  server/        серверная часть (ES-модули), точка входа server/index.js
  web/           собранные страницы (ES-модули), точка входа web/index.js
  migrations/    001_init.sql, 002_…sql — по порядку, каждая один раз
  locales/       переводы модуля: <язык>/<namespace>.js
  docs/          документация администратора, справка, тур, демо-данные
  SIGNATURE      подпись всех файлов пакета
```

`manifest.json`:
```json
{
  "id": "masterplan",
  "name": { "ru": "Мастерплан", "en": "Masterplan" },
  "version": "1.2.0",
  "core": "1.6.0",
  "requires": [{ "id": "crm", "version": "1.1.0" }],
  "enhances": ["contracts", "procurement", "warehouse"],
  "category": "construction",
  "permissions": ["masterplan.admin", "masterplan.sales"]
}
```

## 5. Проверки при установке

Сообщения, которые увидит администратор:

| Проверка | Сообщение при отказе |
|---|---|
| Архив целый, подпись верна | «Файл повреждён или выпущен не нами» |
| Версия ядра (`core`, та же первая цифра) | «Нужно ядро 1.6.0 или новее, у вас 1.5.1» |
| Обязательные модули установлены | «Нужен модуль „CRM“ версии 1.1.0 или новее — он не установлен» |
| Версии обязательных модулей | «Нужен модуль „CRM“ 1.1.0 или новее, у вас 1.0.0» |
| Нет понижения версии | «Установлена 1.3.0, в файле 1.2.0 — понижение запрещено» |
| Обновление не ломает зависимые модули | «„Склад“ 1.4 работает с „Закупками“ 1.x, а в файле 2.0 — сначала обновите „Склад“» |

Удаление запрещено, пока от модуля зависят другие: «Сначала удалите „Склад“ — он использует „Закупки“».

Перед обновлением ядра проверяются все установленные модули. Портал предупреждает, какие из них нужно обновить.

## 6. Этапы

### Этап 1. Развязка модулей
Цель этапа: ни ядро, ни модуль не обращаются к внутренним файлам чужого модуля.
- Правило в CI (dependency-cruiser): модуль может импортировать только ядро и публичный `api.js` модулей из своего `requires`.
- Точки расширения ядра:
  - виджеты дашборда — `registerWidget`;
  - «объекты» — узлы оргструктуры с назначением; модули добавляют свои источники объектов через `registerObjectSource`;
  - шина событий (`contract.signed`, `contract.paid`…);
  - блок «Связи» в карточках;
  - поиск.
- Переносы:
  - синхронизация договор → дом (`contracts/mpSync.js`) уходит в Мастерплан, он подписывается на события договоров;
  - Закупки и Склад выбирают объекты через «объекты» ядра;
  - Контрагенты переходят в ядро;
  - Мастерплан работает с CRM только через `crm/api.js`;
  - Дашборд не импортирует модули.
- Проверка: ядро запускается без каждого из модулей; в CI сборка «только ядро», «ядро + каждый модуль отдельно» и «всё».

### Этап 2. Формат пакета и сборка zip
- Структура папки модуля по разделу 4.
- Версионные миграции вместо `schema()`, которая выполняется при каждом старте. Текущее состояние таблиц принимается за миграцию `001`.
- `make module ID=masterplan`:
  - версия модуля растёт по Conventional Commits, как у портала;
  - сборка `server/` и `web/`;
  - упаковка и подпись;
  - zip кладётся в `dist/modules/`.
- Ключ подписи хранится вне репозитория.
- `web/` собирается как ES-модули. React, antd и SDK портала (`@portal/sdk`: `t`, API-клиент, компоненты ядра) не входят в пакет — модуль берёт их у ядра.

### Этап 3. Загрузчик в портале
- Пакеты лежат в томе данных: `/data/modules/<id>/<version>/`. Таблица `installed_modules`: id, версия, состояние, дата, кто установил.
- Сервер при старте подключает установленные модули из этой таблицы, а не из жёсткого списка.
- Интерфейс получает от сервера список установленных модулей и подгружает их `web/index.js` по требованию. Общие библиотеки ядро отдаёт через import map.
- Портал запускается и без модулей. Если пакет повреждён, портал пропускает его, отмечает ошибку и продолжает работу.

### Этап 4. Установка, обновление, удаление
- Настройки → Модули → «Установить из файла»: загрузка → проверки раздела 5 → карточка модуля (что добавит, какие права, с чем работает) → «Установить» → миграции → перезапуск → модуль «Установлен, выключен».
- Обновление: тот же путь. Перед миграциями делается резервная копия таблиц модуля. Если миграция упала, ставится старая версия и восстанавливаются таблицы.
- Удаление: код удаляется, данные остаются. «Удалить данные» — отдельно, после резервной копии.
- Всё пишется в журнал событий.

### Этап 5. Перевод модулей в пакеты
- Пилот — Мастерплан. Затем CRM, Договоры, Закупки, Склад, Сотрудники, Файловый сервер, Каталог AD.
- Последними — базовые модули, они предустанавливаются из zip, лежащих в образе.
- Заказные модули сразу делаются пакетами.

### Этап 6. Подготовка к магазину
- Идентификатор портала (UUID) и его публичный ключ.
- Формат запроса «какие модули и версии установлены» и «есть ли обновления». Сам магазин — отдельный проект.

## 7. Связь с другими работами

- Языки: у пакета свои переводы в `locales/`, в формате, который строится сейчас. Модуль без перевода на язык показывает английский.
- Ускорение: пакеты подгружаются как отдельные части, только когда человек открывает модуль.
